# Laundry Management System — Payments UI/UX

## 1. Document Purpose

This document defines the V1 UI/UX requirements for the Payments
workflow.

Payments are part of the Order workflow and represent independent
financial transactions associated with an Order.

The feature must support:

    View Order Financial Summary
    +
    Add Payment
    +
    View Payment History
    +
    Display Total Paid
    +
    Display Remaining Amount
    +
    Validate Payment Amount
    +
    Select Payment Method

The feature must follow the approved Product, Domain, Database, API,
Design System, and UI/UX decisions.

---

## 2. Payment UX Goals

The primary goal is:

> Make recording and reviewing payments fast, clear, and financially
> safe.

The operator should always understand:

    Order Total
    +
    Total Paid
    +
    Remaining Amount

before recording a new payment.

---

## 3. Payment Integration with Orders

Payments belong to Orders.

The primary Payment workflow is:

    Order Details
        ↓
    Payment Summary
        ↓
    إضافة دفعة
        ↓
    Payment Form
        ↓
    Confirmation
        ↓
    Local Save
        ↓
    Updated Order Financial Summary

Payments should not require a separate standalone workflow for normal
daily operation.

---

## 4. Payment Methods

The approved V1 Payment Methods are:

    Cash
    InstaPay
    E-Wallet

The UI must use these approved methods.

It must not introduce additional payment methods unless Product/Domain
scope is explicitly changed.

---

## 5. Payment Summary

The Order Details screen should clearly display:

    إجمالي الطلب
    المدفوع
    المتبقي

Example:

    إجمالي الطلب
    500.00 ج.م

    المدفوع
    300.00 ج.م

    المتبقي
    200.00 ج.م

The financial hierarchy should make the remaining amount easy to
identify.

---

## 6. Add Payment Action

The primary action is:

    إضافة دفعة

The action should be available from the Order context when the Domain
rules permit recording a payment.

The user should not need to leave the Order workflow to record a normal
payment.

---

## 7. Payment Form

The Payment form should remain intentionally simple.

Required information:

    المبلغ
    طريقة الدفع

The payment timestamp may be generated by the application according to
the approved Domain behavior.

The user should not be required to enter technical transaction
identifiers.

---

## 8. Payment Amount

The payment amount must be positive.

The UI should validate obvious invalid values before saving.

Example:

    المبلغ يجب أن يكون أكبر من صفر

The Domain layer remains the final authority for payment validation.

---

## 9. Payment Amount Precision

Financial values use the approved integer minor-unit representation.

For EGP:

    1 EGP = 100 minor units

The UI displays normal EGP values to the user.

Example:

    100.50 ج.م

The presentation layer must not use floating-point arithmetic to
determine financial correctness.

---

## 10. Remaining Amount

The remaining amount represents:

    Order Total - Total Paid

The UI must display the value provided by the appropriate
Domain/Application state.

The Payment UI must not implement an independent financial calculation
that could disagree with the Domain layer.

---

## 11. Overpayment

The Payment UI must follow the approved Domain rule for payment amounts.

If overpayment is not allowed, the UI should prevent it and display a
clear message.

Example:

    المبلغ أكبر من المبلغ المتبقي

The UI must not silently reduce the entered amount.

---

## 12. Fully Paid Order

When:

    Remaining = 0

the Order is fully paid.

The UI should clearly communicate:

    تم دفع المبلغ بالكامل

The normal:

    إضافة دفعة

action should no longer be presented as necessary.

The exact action availability remains governed by the Domain rules.

---

## 13. Payment History

Payment History should be visible from Order Details.

Each payment is an independent transaction.

The UI should not present multiple payments as if they were one editable
balance record.

---

## 14. Payment History Information

Each Payment record should display:

    Amount
    Payment Method
    Paid At

Where useful, the UI may also display a concise payment identifier.

Technical UUIDs should not be the primary user-facing identifier.

---

## 15. Payment Method Display

The Payment Method should use clear Arabic labels.

Examples:

    كاش
    InstaPay
    محفظة إلكترونية

The exact final terminology should remain consistent throughout the
application.

---

## 16. Cash Payment

For:

    Cash

the Payment form only requires the payment amount and the selected
method.

No additional financial infrastructure information is required.

---

## 17. InstaPay Payment

For:

    InstaPay

the UI should record the payment using the approved Payment Method.

V1 does not require a payment gateway integration or automatic payment
verification workflow unless explicitly added to Product scope.

The system records the operator's payment transaction.

---

## 18. E-Wallet Payment

For:

    E-Wallet

the UI should record the payment using the approved Payment Method.

V1 does not require automatic wallet provider integration unless
explicitly added to Product scope.

---

## 19. Payment Confirmation

Before saving a payment, the UI may provide a concise confirmation
summary.

Example:

    المبلغ
    200.00 ج.م

    طريقة الدفع
    كاش

Primary action:

    تأكيد الدفع

Secondary action:

    إلغاء

The confirmation should be lightweight and should not unnecessarily slow
down repeated payment entry.

---

## 20. Local Payment Save

Payment creation follows the Offline-first architecture.

The expected flow is:

    User enters Payment
        ↓
    Local Validation
        ↓
    Local Database Transaction
        ↓
    Payment Saved
        ↓
    UI Updated
        ↓
    SyncOperation Created

The user must not need an internet connection to record a valid
payment.

---

## 21. Payment Success Feedback

After a successful local save:

    تم تسجيل الدفعة بنجاح

The Order financial summary should update immediately.

The UI should show:

    Updated Total Paid
    Updated Remaining

---

## 22. Payment Synchronization State

A locally recorded Payment may be waiting for synchronization.

The UI may show:

    في انتظار المزامنة

This must not make the Payment appear unsuccessful.

The Payment has already been persisted locally.

---

## 23. Payment Sync Failure

If remote synchronization fails temporarily:

    Payment remains locally valid.

The UI may show a non-blocking state:

    توجد مشكلة في المزامنة

The Payment must not be duplicated when synchronization is retried.

Idempotency is handled by the Data/Sync/API layers.

---

## 24. Payment Idempotency

Payment creation must be synchronization-safe.

The same Payment must never be created twice because of:

    Network Retry
    Timeout
    Duplicate Request
    Offline Synchronization Retry

The UI does not implement idempotency directly.

It relies on the approved synchronization and API contract.

---

## 25. Payment Editing

Payments are historical financial transactions.

The normal V1 UI should not provide:

    تعديل الدفعة

after the Payment has been persisted.

If a financial correction workflow is introduced later, it must be
defined as a separate business decision.

---

## 26. Payment Deletion

The normal V1 UI should not provide:

    حذف الدفعة

Payments are historical transactions and should not be casually deleted
from the operational interface.

Any future correction/refund/void workflow must be explicitly designed
as a separate Product and Domain decision.

---

## 27. Refunds

V1 does not define a Refund workflow.

The Payment UI must not introduce:

    Refund
    Partial Refund
    Refund History

unless these are explicitly added to Product/Domain scope.

---

## 28. Payment and Order Completion

Payment state is one of the conditions considered by the approved Order
completion workflow.

The UI should communicate when a Payment requirement is preventing
completion.

Example:

    يوجد مبلغ متبقي: 200.00 ج.م

The UI must not independently redefine the completion rule.

---

## 29. Payment Before Storage Completion

The UI should follow the approved Domain rules regarding when payments
can be recorded.

If the Domain permits recording a Payment before all items are stored,
the UI should allow it.

If a specific action is not permitted, the UI should explain the reason.

The UI must not create a new restriction simply for convenience.

---

## 30. Payment Summary in Order List

The Orders list may show a concise payment state.

Examples:

    مدفوع بالكامل
    متبقي 200.00 ج.م

The list should not display the complete Payment History.

---

## 31. Dashboard Payment Information

The Dashboard may display a concise operational metric such as:

    مبالغ متبقية

This is a summary only.

The detailed Payment workflow remains inside Order Details.

---

## 32. Payment Search

V1 does not require a standalone global Payment Search screen.

Payments are primarily accessed through:

    Order Details

The Orders list may provide payment-state filtering.

---

## 33. Payment History Empty State

If an Order has no Payments:

    لم يتم تسجيل أي دفعات

The primary action should be:

    إضافة دفعة

when recording a Payment is allowed.

---

## 34. Payment Loading State

Payment History should load from local data.

Use lightweight loading behavior.

The Payment UI should not block the complete Order screen while remote
synchronization occurs.

---

## 35. Payment Error State

Unexpected local errors should display:

    تعذر تحميل بيانات الدفع

with:

    إعادة المحاولة

Raw database/API errors must not be exposed.

---

## 36. Payment Validation Errors

Common validation messages include:

    المبلغ مطلوب
    المبلغ يجب أن يكون أكبر من صفر
    يجب اختيار طريقة الدفع
    المبلغ أكبر من المبلغ المتبقي

The exact final validation messages should remain consistent with the
application's Arabic UX language.

---

## 37. Payment Method Selection

Payment Method selection should use a clear single-selection component.

Possible UI patterns:

    Segmented Selection
    Radio Options
    Dropdown

The final component should follow the Design System and screen-space
requirements.

The selected method must be visually obvious.

---

## 38. Repeated Payment Entry

The UI should remain efficient for repeated payments across multiple
Orders.

The workflow should not require unnecessary confirmations or navigation
steps.

After recording a Payment, the operator should remain in the relevant
Order context.

---

## 39. Payment Navigation

Primary navigation:

    تفاصيل الطلب
        ↓
    إضافة دفعة

After saving:

    إضافة دفعة
        ↓
    تفاصيل الطلب

The updated financial summary should be immediately visible.

---

## 40. Back Navigation

If the Payment form is opened from Order Details:

    Back
        ↓
    Order Details

The user should not unexpectedly return to the Dashboard.

---

## 41. Payment and Customer

Payments belong to Orders, not directly to Customers.

The UI should therefore not create a standalone Customer Payment
workflow.

Customer history may display Order financial summaries where useful, but
the actual Payment records remain associated with Orders.

---

## 42. Financial Formatting

All displayed monetary values must use the centralized formatting
convention.

Currency:

    ج.م

Example:

    1,250.50 ج.م

The exact thousands/decimal formatting should be implemented through a
shared formatting utility rather than screen-specific formatting.

---

## 43. RTL Requirements

The Payment UI must be fully RTL.

Important areas include:

    Payment Form
    Payment Summary
    Payment History
    Method Selection
    Confirmation Dialog
    Financial Values

Numeric values should remain readable and correctly formatted within
Arabic RTL layouts.

---

## 44. Financial Alignment

Financial amounts should have consistent alignment.

For dense financial information such as:

    Total
    Paid
    Remaining
    Payment Amount

the UI should prioritize scanability.

The exact alignment pattern is defined during visual screen design.

---

## 45. Design System Usage

The Payments feature must use:

    AppColors
    AppTextStyles
    AppTheme
    Shared Components

Likely shared components include:

    AppTextField
    AppButton
    PaymentMethodSelector
    AppCard
    AppDialog
    EmptyState
    LoadingState
    ErrorState

Feature-specific components may be created where justified.

---

## 46. Semantic Colors

Payment states should use semantic Design System colors where
appropriate.

For example:

    Fully Paid
        → Success semantic treatment

    Remaining Amount
        → Attention / Warning treatment when appropriate

    Invalid Payment
        → Error treatment

Color must never be the only indicator.

The actual Arabic label/value must remain visible.

---

## 47. Accessibility

The Payment workflow must provide:

-   Clear field labels
-   Clear currency presentation
-   Clear Payment Method selection
-   Adequate input targets
-   Visible validation
-   Strong contrast
-   Clear confirmation actions
-   Status information that does not rely only on color

---

## 48. Responsive Behavior

The Payment UI must support:

    Desktop
    Tablet
    Smaller supported screens

The Payment form should remain compact.

On smaller screens, financial summary and Payment form may stack
vertically.

The workflow remains the same.

---

## 49. Payment State Model

Payment History should support:

    Initial
    Loading
    Loaded
    Empty
    Error
    Offline
    Syncing
    Sync Attention

Add Payment should support:

    Initial
    Editing
    Validation Error
    Saving
    Saved
    Error

These are Presentation/Application states and must not become new Domain
states.

---

## 50. No Business Logic in UI

The Payment UI must not independently determine:

    Order completion eligibility
    Financial totals
    Payment validity beyond immediate input validation
    Duplicate Payment handling
    Synchronization behavior

These responsibilities belong to the Domain, Repository, and
Synchronization layers.

---

## 51. No Infrastructure Access

The Payment UI must not directly access:

    Dio
    Retrofit
    Supabase
    Edge Functions
    SQLite
    Drift

The approved flow remains:

    UI
        ↓
    Cubit / Bloc
        ↓
    Repository
        ↓
    Local / Remote Data Source

---

## 52. Payment Data Integrity

The UI must treat each Payment as an independent historical transaction.

The following must remain distinct:

    Order Total
    Total Paid
    Remaining
    Individual Payments

The UI must not replace Payment History with a single editable paid
balance.

---

## 53. Payment History Ordering

Payment History should display the most recent Payment first by default.

The exact query and ordering implementation belongs to the Data Layer.

The UI should not expose database-specific ordering mechanisms.

---

## 54. Payment Confirmation Language

Confirmation messages should remain concise and unambiguous.

Example:

    تسجيل دفعة بقيمة 200.00 ج.م بطريقة كاش؟

Actions:

    تأكيد الدفع
    إلغاء

The final wording should remain consistent with the application's
Arabic-first UX.

---

## 55. Payment Workflow Summary

The primary workflow is:

    Order Details
        ↓
    مراجعة الإجمالي والمتبقي
        ↓
    إضافة دفعة
        ↓
    إدخال المبلغ
        ↓
    اختيار طريقة الدفع
        ↓
    تأكيد الدفع
        ↓
    Local Save
        ↓
    تحديث المدفوع والمتبقي
        ↓
    Sync Later

---

## 56. Final Payment UX Principle

> A payment must always be clear, explicit, traceable, and impossible to
> confuse with a simple editable balance.

The operator should always understand:

    How much the Order costs
        +
    How much has been paid
        +
    How much remains
        +
    Which Payments were recorded

while the application remains fast and fully usable offline.
